# 문서 정책

유지되는 Volicord 문서를 변경할 때 이 정책을 사용합니다. 이 문서는 작성자,
검토자, 번역자, 에이전트를 위한 문서 거버넌스 모델을 정의합니다.

이 문서는 유지보수 정책입니다. 제품 동작, API 동작, 저장 효과, 보안 보장,
런타임 동작, 스키마, Core 권한 의미, 적합성 결과, QA 결과, 수락 판단, 닫기
준비 상태, 잔여 위험 판단을 정의하지 않습니다.

## 메타데이터와 문서 종류

유지 문서의 기계 판독 경로는 [`docs/doc-index.yaml`](../../doc-index.yaml)을
사용합니다. 이 메타데이터는 `doc_id`, 유지 경로, 문서 `kind`, 요약, 규범 수준,
번역 정책, 주요 독자, 독자 여정, 필요한 경우의 집중 `canonical_for` 담당 범위,
유지보수 `owner_area`, `created_on`, `last_updated_on`, `last_verified_on`, 루트
`default_applicability`, 항목별 선택 `applies_to`, `depends_on` 관계, 대응 문서의
선택적이고 정확한 의미 기반 `contracts`를 기록합니다. 일반 API 메서드 경로에서는
요청과 응답 계약 ID를 결정적으로 도출합니다. 그 밖의 계약 포함 문서는 실제로
다루는 의미 기반 계약 ID만 나열합니다.

`canonical_for`는 문서가 담당하는 정보 또는 계약 영역을 이름 붙입니다.
`owner_area`는 그 항목을 정확하게 유지하는 오래 유지될 책임 영역을 이름
붙입니다. 두 필드는 관련되어 있지만 서로 대체할 수 없습니다.

날짜는 `YYYY-MM-DD`를 사용합니다. `created_on`은 유지 파일 또는 한영 대응
쌍의 검증 가능한 최초 도입일을 기록합니다. `last_updated_on`은 그 파일 또는
대응 쌍의 검증 가능한 최신 내용 변경일을 기록합니다. `last_verified_on`은
색인된 경로, 메타데이터, 링크, 대응 관계, 담당 경로를 유지보수 정책에 따라
확인한 날짜입니다. 이것은 제품 수락, 런타임 적합성, QA 완료, 닫기 준비 상태,
보안 증명, 잔여 위험 수락이 아닙니다. 적용 가능성 카탈로그 키는 릴리스, 스키마,
도구 체인 번호를 넣지 않은 안정적인 의미 식별자를 사용합니다. 각 카탈로그 항목은
`version_source`로 담당 파일이나 레지스트리를 지정하고 유지보수 도구는 그 담당
원본에서 현재 값을 읽습니다. `default_applicability`의 비어 있지 않은 목록은 모든
항목에 적용됩니다. 각 항목의 `applies_to`는 비어 있지 않은 추가 카탈로그 값에만
사용하며 루트 기본값을 반복하지 않습니다.

문서 종류는 독자 목적에 따라 사용합니다.

- `landing`: 제품, 저장소, 문서 영역을 소개합니다.
- `tutorial`: 실행 가능한 순서로 독자를 안내합니다.
- `how_to`: 구체적인 작업을 끝내는 방법을 설명합니다.
- `explanation`: 개념, 아키텍처, 근거, 코드 구조를 가르칩니다.
- `reference`: 정확한 제품 계약을 담당하거나 참조 문서 안에서 독자를
  안내합니다.
- `maintenance`: 문서 작성자, 번역자, 검토자, 에이전트를 안내합니다.

대부분의 랜딩, 튜토리얼, 방법 안내, 설명 문서는 `canonical_for`를 갖지
않아야 합니다. 문서가 정의된 주제의 안정적인 담당 문서일 때만
`canonical_for`를 사용합니다. 특히 집중 참조 계약과 유지보수 정책이 여기에
해당합니다.

구조화 번역, 표현, 식별자 보존 정책은
[`docs/terminology-map.yaml`](../../terminology-map.yaml)을 사용합니다. 정확한
공개 API 필드와 값은 생성 공개 JSON Schema의 의미 기반 설명자에서, CLI 문법과
값은 `volicord-command-model`에서, CLI inbox 출력은 사용자 행동 표현 담당
원본에서, 진단 코드는 typed 진단 레지스트리에서, 프로토콜 식별자는 현재
프로토콜 레지스트리에서 가져옵니다. 문서 색인은 식별자 배열을 메타데이터에
복사하지 않고 이 의미 기반 계약을 참조합니다. 용어 지도는 API, 저장소, 스키마,
보안, 상태 보기, 프로토콜, 진단, 런타임 계약을 정의하거나 목록화하지 않습니다.

Volicord 브랜드 표기, 공식 한영 브랜드 문구, 구성 요소 표현, 프로젝트 안에서
사용하는 시각 원칙, 브랜드 주장 경계는 [브랜드 지침](brand-guidelines.md)을
유지보수 담당 문서로 사용합니다. 브랜드 지침은 제품 동작, API 동작, 저장 효과,
스키마, 보안 보장, Core 권한 의미를 정의하지 않습니다.

Volicord 제품 정체성, 서비스 계획 원칙, 문서 역할, 코드 지침 경계, 테스트 철학,
호환성 규율, 길이 기준 거부를 위한 오래 유지될 유지보수
헌장은 [제품 및 유지보수 헌장](product-maintenance-charter.md)을 사용합니다.
이 헌장은 정확한 계약을 집중 참조 담당 문서 밖으로 옮기지 않습니다.

주요 문서와 문서 계열이 무엇을 담당하고, 제외하고, 그림으로 보여 주고, 연결해야
하는지 판단할 때는 [문서 헌장](document-charters.md)을 사용합니다. 헌장은
메타데이터 모델을 방문이 많은 문서의 실무 범위 지침으로 바꾸며, 정확한 제품
계약을 집중 참조 담당 문서 밖으로 옮기지 않습니다.

그림을 만들고, 검토하고, 캡션을 붙이고, 유지할 때는 [그림 정책](diagram-policy.md)을
사용합니다. 그림 정책은 그림 범주, 캡션 기준, 화살표 의미, 정확성 담당자,
배치 경계를 정의하여 사용자 작업 흐름 그림, 구성 요소 지도, 런타임 순서,
권한 모델, 저장 생명주기, 연결 설정 흐름, 의존성 그래프가 서로 섞이지 않게
합니다. 또한 작성과 검토에 쓰는 메타데이터를 독자용 산문과 분리합니다. 일반
README, 사용자 가이드, 참조, 아키텍처 가이드 문서는 `Diagram role:`이나 `그림 역할:` 같은 문자
그대로의 라벨을 노출하지 말고, 자연스러운 캡션이나 주변 산문으로 그림의 목적을
설명해야 합니다.

## 표면 안정성 라벨

유지 담당 문서가 공개 계약, 변화 가능한 로컬 통합 표면, 구현 세부사항, 진단 출력을
구분해야 할 때는 아래의 작은 어휘를 사용합니다. 이 라벨은 문서화된 표면을 분류할
뿐이며, 스키마 버전, 마이그레이션 버전, 별도 API 버전, 레거시 호환 경로,
저장소 업그레이드 경로, 대체 동작을 만들지 않습니다.

| 라벨 | 의미 |
|---|---|
| `stable` | 구현과 통합이 의존하도록 의도된 문서화된 공개 또는 기준 계약입니다. |
| `beta` | 현재 작업 공간에서 지원되지만 담당 문서가 정한 경계 안에서 계속 변할 수 있는 문서화된 표면입니다. |
| `internal` | 공개 계약이나 일반 사용자 대상 선택자가 아닌 구현, 저장소, 프로세스 바인딩, 생성 래퍼, 어댑터 세부사항입니다. |
| `diagnostic` | 사람이 읽는 요약, 보고서, 상태 점검 화면, 고지 문구, 문제 해결 출력입니다. 구조화 필드와 안정적인 ID는 집중 담당 문서가 명시할 때만 계약입니다. |

공개, beta, internal, diagnostic 표면을 정의하는 집중 참조 담당 문서는 안정적인
앵커 `<a id="surface-stability"></a>`가 있는 짧은 표면 안정성 섹션을
포함해야 합니다. 섹션은 간결하게 유지하고, 가능한 가장 좁은 표면 단위로 라벨을
사용하며, 긴 설명을 반복하지 말고 이 어휘로 연결합니다. 집중 담당 문서의 근거 없이
현재 stable 계약을 낮은 안정성으로 표시하면 안 됩니다.

## 담당 경계

정확한 제품 계약은 `doc-index.yaml`이나 [참조 색인](../reference/README.md)에서
선택한 집중 참조 담당 문서에 둡니다. 여기에는 기준 범위, API 동작, 스키마
의미, 오류 의미, 저장 효과, 보안 표현, 접근 경계, 닫기 준비 상태 의미, 제품
용어, 지원 범위 밖 기능의 승격 규칙, 값 집합 의미가 포함됩니다.

독자용 문서는 계약 자료를 요약하거나 설명하거나 가르치거나 순서화할 수
있지만, 정확한 동작이 중요할 때는 집중 참조 담당 문서로 연결해야 합니다.
가이드, 튜토리얼, 방법 안내, 설명 문서, README, 경로 문서, Maintain 문서,
`AGENTS.md`, 예시, 구현 주석, 테스트, 픽스처, CLI 도움말, 생성 출력이 두 번째
계약 본문이 되면 안 됩니다.

중복은 문구 유사성이 아니라 정보 담당 범위로 판단합니다. 짧은 안내 문구의
반복은 유용할 수 있습니다. 그러나 API 동작, 스키마 필드, 저장 효과, 보안
보장, 값의 의미, 담당 문서 지도를 반복하면 그 내용이 해당 문서의 담당 범위에
속하지 않는 한 경쟁하는 권한이 생깁니다.

필요한 규범 의미의 집중 담당 문서가 없으면 담당 문서 공백을 보고하거나 먼저
적용되는 담당 문서를 갱신합니다. 담당 문서가 아닌 곳에서 그 공백을 메우지
않습니다.

기준 동작은 예약된 값, 프로필 조건부 값, 지원 범위 밖 자료와 구분합니다. 값
이름이 스키마, 예시, 저장소 메모, 경로 문서에 등장해도 기준 동작이 되는 것은
아닙니다.

## 아키텍처 설계 참조

유지되는 현재 상태 아키텍처 설계 문서 계열은
[`docs/en/architecture-guide/design/`](../../en/architecture-guide/design/README.md)과
[`docs/ko/architecture-guide/design/`](../architecture-guide/design/README.md)에
있습니다. 개별 설계 문서는 현재 존재하는 구현을 설명합니다. 시간순 결정 기록,
검토 보고서, 마이그레이션 가이드, 릴리스 이력이 아닙니다.

문서 계열 색인을 제외한 모든 현재 아키텍처 설계 문서는 H1 제목 하나 뒤에 아래
H2 절을 정확히 이 순서로 사용합니다.

1. `목적`
2. `설계`
3. `불변 조건`
4. `책임 경계`
5. `실행 흐름`
6. `실패 동작`
7. `범위 제외`
8. `구현 경로`
9. `참조 담당 문서`

대응 영어 문서는 의미가 같은 `Purpose`, `Design`, `Invariants`,
`Responsibility boundaries`, `Execution flow`, `Failure behavior`, `Scope
exclusions`, `Implementation routes`, `Reference owners` 순서를 사용합니다.
문서 계열 색인은 개별 설계 문서가 아니라 독자 경로로 유지합니다. 개별 설계
문서는 이 긍정적인 스키마 밖의 중첩 제목 절을 추가하지 않습니다.

설계 문서는 현재 구현 구조, 모듈 책임, 실행 흐름, 오래 유지될 구현 불변 조건을
담당합니다. 정확한 제품 동작, 스키마 의미, 저장 효과, 보안 보장, Core 권한 의미는
집중 참조 담당 문서에 두고 `참조 담당 문서` 절에서 연결합니다.

아키텍처 설계 문서는 긍정적인 제목 스키마가 설명하는 현재 구현 구조만 담습니다.
각 현재 설계는 유지되는 경로 하나로 표현하며 중복 표현이나 숫자 버전으로 선택하는
표현을 두지 않습니다. 구조 검증은 제목 스키마를 적용하며 산문 품질은 담당 문서와
사람 검토의 관심사로 남습니다.

## 예시와 소스 링크

예시는 오래 유지되고 자체적으로 이해되는 제품 또는 사용자 시나리오여야
합니다. 예시는 문서화된 형태를 보여 주는 자료이며 제품 정책을 만들지
않습니다.

예시 경로, 자리표시 값, 샘플 파일 이름은 긍정적으로 설명합니다. 그 값이
독자에게 무엇을 뜻하는지, 예를 들어 Product Repository 예시 경로나 권한 번들
출력 경로임을 말합니다. 부정문은 안전, 권한, 경로 지정, 지속 저장,
사용자 결정 경계를 지킬 때 사용합니다.

API 메서드 참조 예시는 메서드 안에서만 성립해야 합니다. 필요한 모든 참조,
`state_version` 사실, 아티팩트 참조, 실행 참조, 판단 참조, 차단 사유 참조,
파일 경로를 메서드 문서 안에서 도입하거나 메서드 안의 전제로 밝혀야 합니다.
메서드 참조 문서들 사이에 공유 시나리오 축을 만들지 않습니다.

예시는 필요에 따라 메서드 담당 문서, 스키마 담당 문서, 값 집합 담당 문서,
저장 효과 담당 문서를 기준으로 검토합니다. 지원되지 않는 enum 형태 값, 오래된
응답 형태, 맞지 않는 필수 필드, 일관되지 않은 응답 분기는 문서 오류입니다.

참조 문서의 모든 `json`, `yaml`, `yml` 펜스는 완전한 구조화 인스턴스입니다.
각 펜스는 `shape=` 값을 정확히 하나 선언합니다. 문서 경로가 사용 가능한 의미
기반 계약을 정하며, 그중 둘 이상의 계약이 같은 형태를 제공하면 펜스는 문서에
이미 지정된 계약 하나를 `contract=` 값으로 정확히 하나 선언합니다. 펜스
메타데이터에는 식별자 목록을 넣지 않습니다.

선택된 설명자가 선택된 형태의 정확한 스키마를 제공합니다. 현재 형태는
`complete_request`, `params`, `complete_response`, `response_variants`,
`result_body`, `rejection`, `dry_run`, `schema_object.<name>`, `cli_output`, `mcp_request.<tool>`,
`mcp_response.<tool>`과 설명자가 제공하는 `persisted_object.<name>` 또는
`diagnostic_object.<name>`입니다. 설명자는 현재 담당 원본이 지원하는 형태만
제공합니다. `schema` 펜스는 독자를 위한 형식 또는 형태 표기이며 JSON이나 YAML
인스턴스가 아닙니다.

구조화 JSON 객체와 YAML 매핑에서는 모든 중첩 깊이의 각 객체 또는 매핑 안에서
키가 정확히 하나씩만 나타나야 합니다. 파서는 JSON 호환 값을 만들기 전에 같은
키의 두 번째 등장을 거부합니다. 구조화 YAML에서는 태그, 앵커, 별칭, 병합 키,
문자열이 아닌 매핑 키도 거부합니다. 고유 키로 구성된 값은 필수 속성, 알 수
없는 속성, 형식, 중첩 객체와 배열, enum과 const 값, 제약 조건, 판별 union,
참조, Null 허용 여부를 포함해 선택된 정확한 생성 스키마를 만족해야 합니다.
영어와 한국어 인스턴스는 각각 파싱하고 검증한 뒤 구조와 정확한 식별자 동등성을
비교합니다.

API 메서드 참조의 요청 및 응답 필드, 필수 여부, Null 허용 여부, 형식 표는
`cargo run -p xtask -- docs-sync`가 의미 기반 요청 및 응답 설명자에서 생성합니다.
안정적인 생성 영역 표식은 각 표를 정확한 계약 ID와 형태에 결합합니다. 공유
`ToolResultBase`, `ToolRejectedResponse`, `ToolDryRunResponse` 구조는 API 코어
스키마에서 한 번 생성하고, 메서드 문서는 그 공유 구조로 가는 링크를 생성하여 성공
결과 필드와 구분합니다. 작성자는 생성 영역이나 두 번째 완전한 필드 목록이 아니라
주변의 의미, 정책, 효과, 필드 간 불변 조건, 실패 동작을 편집합니다.

같은 명령은 `workspace.metadata.architecture.packages`에서 영어·한국어 아키텍처
문서의 패키지 책임 및 의존 방향 표를 생성하며, 이 표를 두 번째 패키지
레지스트리로 수동 관리하지 않습니다.

소스 코드 링크와 아키텍처 가이드 문서는 오래 유지될 크레이트, 모듈, 진입점, 실행
단계, 책임 경계를 설명해야 합니다. 줄 번호에 기대는 설명, 비공개 도우미
목록, 구현 이력은 피합니다. 코드 구조가 오래 유지될 방식으로 바뀌면 같은 문서
변경 범위에서 관련 아키텍처 가이드 문서, 특히 [아키텍처](../architecture-guide/architecture.md)를
갱신합니다.

## 오래 유지되는 문서 내용

유지 문서는 안정적인 현재 모델을 설명해야 합니다. 작업 이력, PR 메모,
마이그레이션 설명, 부수 메모, 생성된 런타임 기록, 보관 사본, 변환 메모,
미해결 검토 메모, 작업 로그, 작업별 후속 계획을 유지 문서에 저장하지
않습니다.

유지 문서, 공유 메타데이터, README 파일, `AGENTS.md` 파일은 Volicord Runtime Home이
아닙니다. 런타임 데이터, 생성 로그, SQLite 파일, 제품 런타임 홈, 테스트
런타임 홈, 생성된 상태 보기, 픽스처 출력, QA 결과, 수락 기록, 닫기 준비 상태,
잔여 위험 기록을 여기에 저장하지 않습니다.

문서 도구가 편집이나 검증 중 생성 출력을 만들었다면 일반적인 무시된 빌드 출력이
아닌 한 끝내기 전에 제거합니다.

## 범위별 작업 규칙

저장소 파일을 변경하기 전에 루트 [`AGENTS.md`](../../../AGENTS.md)를 읽습니다.
`docs/` 아래에서는 [`docs/AGENTS.md`](../../AGENTS.md)도 읽습니다. 문서와 Rust
구현 경계를 함께 다루는 작업에서는 [`crates/AGENTS.md`](../../../crates/AGENTS.md)도
읽습니다.

`AGENTS.md` 파일은 저장소 작업 지침입니다. 제품 계약, 런타임 동작, API 동작,
저장 효과, 보안 보장, Core 권한 의미를 정의하지 않습니다.

유지 문서를 추가, 제거, 이름 변경, 용도 변경할 때는 같은 변경 안에서
`doc-index.yaml`, 대응 언어 경로, 독자 탐색 경로, 용어 경로, 링크를 함께
갱신합니다.
