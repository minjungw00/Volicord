# 제품 및 유지보수 헌장

Volicord의 오래 유지될 서비스 방향, 문서 역할, 구현 지침, 테스트, 브랜드 언어,
번역 정책을 계획할 때 이 헌장을 사용합니다. 이 문서는
[문서 정책](documentation-policy.md), [문서 헌장](document-charters.md),
[브랜드 지침](brand-guidelines.md), [번역 정책](translation-policy.md),
[검증](validation.md), 집중 [참조 색인](../reference/README.md)을 보완합니다.

이 문서는 유지보수 헌장입니다. 제품 동작, 공개 API 동작, 저장 효과, 보안 보장,
런타임 동작, 스키마, Core 권한 의미, 적합성 결과, QA 결과, 수락 판단, 닫기
준비 상태, 잔여 위험 판단을 정의하지 않습니다.

## 제품 정체성

- Volicord는 AI 지원 제품 작업을 위한 로컬 작업 권한 기록입니다.
- Core는 Volicord 상태를 위한 로컬 기준 기록입니다. Core의 정확한 상태 권한 역할을
  공개 Volicord 제품 정체성으로 합치지 않습니다.
- 사용자 판단은 에이전트 행동과 구분된 채 남아야 합니다. Volicord는 판단이 필요한
  경계를 기록하고, 경로를 잡고, 보존하고, 보여 줄 수 있지만 사용자 소유 결정을
  대신하는 것으로 표현하면 안 됩니다.
- 권한 기록은 OS 수준 강제가 아닙니다. 권한 기록은 로컬 기록과 작업 흐름 통제이지
  샌드박스, 명령 감시기, 파일 시스템 격리 계층, 네트워크 격리 계층, 보안 증명,
  에이전트가 지시를 따랐다는 보장이 아닙니다.
- 범위, 증거, 쓰기 티켓, 쓰기 승인, 최종 수락, 잔여 위험 수락, 닫기 상태는
  계획, 문서, 코드, 테스트, 보고에서 서로 구분합니다.

## 서비스 계획 원칙

서비스 작업은 명시적 범위, 보이는 증거, 사용자 소유 판단, 기록된 상태 전이,
정직한 닫기 상태 점검을 중심으로 계획합니다. 기능은 사용자가 에이전트와
함께 그 경계를 더 쉽게 볼 수 있게 해야 하며, 다듬어진 요약 뒤에 숨기면 안 됩니다.

호스트 통합과 관찰 표면은 집중 참조 담당 문서가 더 강한 보장을 정의하지 않는 한
협력적이고 탐지적인 표면입니다. 제품 언어, 구현 주석, 테스트, CLI 도움말, 생성
지침, 예시는 관련 참조 담당 문서가 뒷받침하는 것보다 강한 보호를 암시하면 안
됩니다.

Volicord가 첫 주요 릴리스에 준비되기 전에는 목표 지향 설계 작업에 더 정돈된 제품
모델이 필요할 때 저장소가 레거시 CLI, API, 저장소, 픽스처, 문서 호환성을 보존할
필요가 없습니다. 오래된 형태가 의도한 모델과 충돌하면, 단지 예전에 존재했다는
이유로 이전 동작을 보존하지 말고 집중 참조 담당 문서, 구현, 예시, 유지 문서를
함께 갱신합니다.

서비스 계획의 비목표에는 편집기, 셸, 테스트, 코드 리뷰, 사용자 판단을 대체하는
것, OS 보안 경계로 동작하는 것, 모든 쓰기가 안전하다고 증명하는 것, 에이전트
요약을 Core 권한 기록으로 만드는 것이 포함됩니다.

## 문서 역할

| 범주 | 의도한 역할 |
|---|---|
| [루트 README](../../../README.ko.md) | 첫 사용자를 위한 기반 설명과 기본 제품 설명입니다. 독자에게 방향을 잡아 주고, 일반적인 첫 경로를 보여 주며, 초보자 개념을 소개해야 합니다. 순수 링크 경로 안내서나 전체 참조 매뉴얼이 되면 안 됩니다. |
| Maintain 문서 | 제품 원칙, 브랜딩, 서비스 계획 목표, 코드 지침, 문서 문체, 테스트 철학, 번역 정책, 검증 경계, 담당 경로 관행을 담당합니다. 정확한 제품 계약을 다시 정의하지 않고 유지보수자를 안내합니다. |
| 사용자 문서 | 설치, 설정, 일반 작업 흐름, 문제 해결, 사용자와 에이전트의 협업, 예시를 위한 실무 도움말입니다. 사용자를 위해 동작을 요약할 수 있으며, 정확한 동작이 중요할 때는 참조 문서로 연결해야 합니다. |
| 계약 및 참조 문서 | 공개 동작, 지원 범위, API, 저장소, 전송, 보안 경계, 스키마, 값 의미, 오류 동작, 그 밖의 정확한 제품 계약을 담당합니다. |
| 아키텍처 가이드 문서 | 계약 세부사항을 넘어서는 아키텍처와 구현 이해를 담당합니다. 소스 구조, 요청 흐름, 설계 패턴, 테스트 전략, 변경 작업 흐름, 오래 유지될 구현 근거가 여기에 속합니다. |

주요 문서 계열의 자세한 담당 규칙은 [문서 헌장](document-charters.md)을
사용합니다.

## 코드 지침

구현 작업은 계약 우선입니다. 코드 변경에 집중 담당 문서가 정의하지 않은 동작이
필요하면 먼저 적용되는 참조 담당 문서를 갱신하거나 담당 문서 공백을 보고합니다.
코드, 테스트, 픽스처, 예시, 생성 출력, CLI 도움말, 구현 주석이 제품 동작이
정의된 유일한 위치가 되면 안 됩니다.

Core 쪽 코드는 CLI와 MCP 어댑터 계층에서 독립적으로 유지합니다. CLI와 MCP 어댑터는
Core 쪽 인터페이스를 호출할 수 있습니다. 코드는 효과 경로, 상태 전이, 효과 없음
분기, 사용자 판단 경로, 닫기 차단 사유를 추론하기 쉽게 만들어야 합니다.

아키텍처 가이드 문서는 오래 유지될 소스 구조를 따라야 합니다. 구현 변경이 크레이트 역할,
모듈 책임, 요청 흐름, 테스트 전략을 오래 유지될 방식으로 바꾸면 적용되는
[아키텍처 가이드](../architecture-guide/README.md)를 갱신합니다.

## 품질 기준과 길이

파일 길이, 문서 길이, LOC 수는 Volicord 코드나 문서의 하드 품질 기준이 되면 안
됩니다. 숫자는 담당 범위가 분명한지, 계약이 정확한지, 예시가 맞는지, 상태 전이가
테스트되는지, 첫 독자가 작업 흐름을 완료할 수 있는지 증명하지 못합니다.

하드 길이 제한은 잘못된 유인을 만듭니다. 개수만 맞추려고 집중된 자료를 나누면
담당 문서가 정의한 계약이 흩어지고, 설명이 중복되며, 독자 경로가 더 어려워질 수
있습니다. 긴 파일이나 문서는 담당 범위, 가독성, 검토 가능성, 소스 구조가 나아질
때 나누며, 줄 수가 기준을 넘었다는 이유만으로 나누지 않습니다.

위험에 맞는 품질 통제를 사용합니다. 담당 경로, 계약 정확성, 독자 사용성, 한영
의미 일치, 링크 무결성, 소스 정합성, 오래 유지될 테스트, 검증 명령이 그 기준입니다.

## 테스트 철학

저장소 테스트는 오래 유지될 동작, 계약, 상태 전이, 사용자 가치, 안정적인 추상화
경계, 유지되는 문서 규칙을 검증해야 합니다. 테스트 이름은 보호하는 현재 제품
동작이나 유지보수 규칙을 기준으로 짓습니다.

일회성 정리 테스트는 커밋하지 않습니다. 오래된 용어, 플래그, 필드, 예시, 구현
세부사항이 사라졌다는 사실만 증명하는 검색은 변경 절차 안의 감사이지 오래
유지될 저장소 테스트가 아닙니다. 어떤 부재가 오래 유지될 계약으로 중요하다면
현재 공개 CLI 옵션 집합, 현재 저장소 스키마, 현재 MCP 노출 스키마, 현재 용어 역할
메타데이터처럼 현재의 긍정적 형태를 테스트합니다.

테스트 결과는 구현 또는 유지보수 점검입니다. 테스트는 제품 계약을 정의하거나,
보안을 증명하거나, QA를 완료하거나, 닫기 상태를 확립하거나, 최종 수락을
기록하거나, 잔여 위험을 수락하지 않습니다. 배치와 보고 경계는
[검증](validation.md)과 [테스트 전략](../architecture-guide/testing-strategy.md)을
사용합니다.

## 브랜드와 번역

Volicord 표기, 공식 한영 문구, 구성 요소 표현, 시각 원칙, 주장 경계는
[브랜드 지침](brand-guidelines.md)을 사용합니다. 브랜드 언어는 판단이 사용자에게
남는다는 점을 지켜야 하며, 권한 기록이 OS 수준 강제처럼 들리게 하면 안 됩니다.

한영 의미 일치, 자연스러운 한국어 기술 문체, 식별자 보존, 용어 경로 지정은
[번역 정책](translation-policy.md)과
[`docs/terminology-map.yaml`](../../terminology-map.yaml)을 사용합니다. 영어와
한국어 Maintain 문서는 첫 주요 릴리스 전 호환성 지침, 길이 기준 거부, 오래
유지될 테스트 철학, 사용자 판단 경계를 포함해 같은 원칙을 의미 단위로 담아야
합니다.

## 유지보수 완료 기준

유지되는 경로, 역할, 담당 문서, 경로가 바뀌면 같은 변경에서
[`docs/doc-index.yaml`](../../doc-index.yaml), 대응 언어 경로, 독자 탐색 경로를
갱신합니다. 적용되는 문서 검증을 실행하고 결과는 저장소 파일이 아니라 대화에
보고합니다.

작업별 계획, 작업 로그, 생성 기록, 런타임 홈, SQLite 파일, 생성 로그, 보관 사본,
로컬 런타임 출력을 유지 문서에 남기지 않습니다.
