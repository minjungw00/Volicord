# Implementation design patterns

This guide explains stable implementation structures visible in the current
Rust workspace. It is an Architecture Guide document: it names problems,
source locations, benefits, trade-offs, and tests, but it does not define
public API behavior, schemas, storage effects, security guarantees, runtime
behavior, or Core authority semantics.

Use wording such as "resembles" or "functions as" here deliberately. The
source shows durable structures, but this page does not claim formal pattern
intent beyond what the code demonstrates.

For exact product behavior, use the [Reference Index](../reference/README.md).
For the broad crate map, use [Implementation Architecture](architecture.md);
for representative method traces, use [Request Lifecycle](request-lifecycle.md).

## Pattern map

| Structure | Problem addressed | Source locations and symbols | Benefit | Trade-off | Tests |
|---|---|---|---|---|---|
| Ports-and-adapters-like dependency direction | Public method behavior needs to stay independent of transport and setup entry points. | [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs) for `CoreService`; [`crates/volicord-mcp/src/adapter.rs`](../../../crates/volicord-mcp/src/adapter.rs) for `McpAdapter`; Cargo manifests for `volicord-core`, `volicord-mcp`, and `volicord-cli`. | Core can be exercised directly and through MCP without adapter-owned method semantics. | Adapter startup and session validation still need Store access, so readers must separate startup validation from public method execution. | `status_is_read_only_including_dry_run` in [`crates/volicord-core/src/methods/tests/status.rs`](../../../crates/volicord-core/src/methods/tests/status.rs); `mcp_status_does_not_advance_state_version` in [`crates/volicord-mcp/src/tests/tool_calls.rs`](../../../crates/volicord-mcp/src/tests/tool_calls.rs); `connection_invocation_is_injected_and_single_project_is_auto_selected` in [`tests/integration/mcp_connection.rs`](../../../tests/integration/mcp_connection.rs). These tests cover separate layer properties rather than full response equivalence. |
| Application-service-like `CoreService` | Public methods need a single adapter-independent entry point over Runtime Home, ID generation, time, Store access, and response construction. | `CoreService`, `CoreService::prepare_request`, and `CoreService::execute_prepared_request` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs); method entry functions in [`crates/volicord-core/src/methods/`](../../../crates/volicord-core/src/methods/). | Common preflight and response rules are centralized while method files keep method-specific planning. | `CoreService` becomes a coordination point; changes to common preflight can affect every method branch. | Pipeline tests such as `rejected_branch_has_no_storage_effect`, `committed_mutation_increments_state_version_once`, and `operation_category_mismatch_is_rejected_without_effect` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs). |
| Reusable policy object | Method preflight needs consistent access, Task, replay, freshness, and effect requirements without duplicating the sequence in each method. | `MethodPolicy`, `TaskRequirement`, `ReplayPolicy`, `FreshnessPolicy`, and `MethodEffectPolicy` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs); `mutation_method_policy` in [`crates/volicord-core/src/methods/mod.rs`](../../../crates/volicord-core/src/methods/mod.rs). | Method code declares the required policy while the shared pipeline owns the ordering. | A policy is only the common gate. Method-specific compatibility still lives in planners and Reference owners. | `stale_expected_state_version_is_rejected_without_effect` and `idempotency_replay_returns_stored_response` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs). |
| Typed planning before effect execution | Methods need to decide validation, method-specific result fields, events, and storage mutations before any normal Core mutation is committed, while common result facts remain unknown. | `MethodResultFields` and method-result declarations in [`crates/volicord-types/src/methods.rs`](../../../crates/volicord-types/src/methods.rs); `plan_intake` in [`crates/volicord-core/src/methods/intake.rs`](../../../crates/volicord-core/src/methods/intake.rs); `plan_prepare_write` in [`crates/volicord-core/src/methods/prepare_write.rs`](../../../crates/volicord-core/src/methods/prepare_write.rs); generic `OwnerPipelineBranch<F>` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs). | One declaration supplies both the fields-only planning type and complete public result shape. The pipeline keeps method fields typed across branch selection and constructs a complete result only after common branch facts are known. | A public result-field change must update its one declaration and the affected planner projections; the shared pipeline remains responsible for attaching effect, state-version, event, and replay facts. | `method_result_fields_compose_every_affected_public_result_schema` in [`crates/volicord-types/src/lib.rs`](../../../crates/volicord-types/src/lib.rs); `no_effect_result_branch_composes_typed_fields_without_storage_effect` and `committed_mutation_increments_state_version_once` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs); method contract tests under [`crates/volicord-core/src/methods/tests/`](../../../crates/volicord-core/src/methods/tests/). |
| Grouped command-like storage mutation values | Method planners need a typed way to tell Store what to apply without embedding SQL or storage ordering in method code, while persistence remains owned by each aggregate. | The grouped `CoreStorageMutation` dispatcher in [`crates/volicord-store/src/core_pipeline/mutations.rs`](../../../crates/volicord-store/src/core_pipeline/mutations.rs); aggregate enums and application SQL in `tasks.rs`, `change_units.rs`, `write_tickets.rs`, `runs.rs`, `evidence.rs`, `artifacts.rs`, `user_actions.rs`, and `continuity.rs`; workflow-policy mutation application in `workflow_records.rs`; ordered lists built by method planners such as `intake.rs`, `prepare_write.rs`, and `record_run.rs`. | Store aggregates own persistence mechanics, the coordinator owns only cross-aggregate transaction concerns, and Core planners own method intent. | A new persistent effect must route through its aggregate enum and tests; only a genuinely new responsibility adds another top-level group. Exact behavior still belongs to Reference owners. | Aggregate-local mutation validation tests; `ordered_multi_aggregate_commit_is_versioned_replayable_and_durable` and `intermediate_aggregate_failure_rolls_back_every_commit_effect` at the Store commit boundary; method effect tests under [`crates/volicord-core/src/methods/tests/`](../../../crates/volicord-core/src/methods/tests/). |
| Explicit transaction and atomic commit boundary | Normal committed method effects need replay, freshness, state-version change, events, response JSON, and storage mutations to succeed or fail together. | `CommitMutationInput`, `CommittedMutationFacts`, `MutationCommitOutcome`, and `CoreProjectStore::commit_mutation` in [`crates/volicord-store/src/core_pipeline/`](../../../crates/volicord-store/src/core_pipeline/); `begin_immediate_transaction` in [`crates/volicord-store/src/sqlite.rs`](../../../crates/volicord-store/src/sqlite.rs). | Commit behavior has one Store boundary instead of many partial writes. | Non-commit effect paths, especially transient artifact staging, must be documented and tested separately. | Store transaction tests such as `transaction_replay_returns_stored_response_before_stale_expected_state` and `transaction_replay_hash_conflict_rejects_without_effect`; pipeline test `committed_mutation_increments_state_version_once`. |
| Injectable clock | Authority-sensitive timestamps need deterministic tests without replacing production time behavior. | `Clock`, `SystemClock`, `CoreService::with_clock`, and `CoreService::now` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs); `ManualClock` in [`crates/volicord-core/src/methods/tests/mod.rs`](../../../crates/volicord-core/src/methods/tests/mod.rs); `FixedClock` in [`tests/conformance/baseline.rs`](../../../tests/conformance/baseline.rs). | Expiry, staging, and time-bound behavior can be exercised predictably. | Code that needs time must receive it through Core rather than calling the system clock directly. | Time-sensitive method tests under [`crates/volicord-core/src/methods/tests/`](../../../crates/volicord-core/src/methods/tests/) and conformance scenarios using `CoreService::with_clock`. |
| Opaque identifier newtypes | IDs need type separation while staying serializable as strings. | `opaque_string_type!` and wrappers such as `ProjectId`, `TaskId`, `RequestHash`, and `WriteTicketId` in [`crates/volicord-types/src/ids.rs`](../../../crates/volicord-types/src/ids.rs). | Rust catches many accidental ID-family mixups, and serde still exposes the documented string-shaped API shape. | The wrapper does not itself validate product meaning; validation and authority stay with owners and implementation checks. | `sequence_generator_preserves_kind_prefixes` in [`crates/volicord-types/src/ids.rs`](../../../crates/volicord-types/src/ids.rs) and request-shape tests in [`crates/volicord-types/src/lib.rs`](../../../crates/volicord-types/src/lib.rs). |
| Enum-based controlled values | Public value sets and storage-facing controlled names need typed handling in Rust. | `MethodName`, `OperationCategory`, `ResponseKind`, `EffectKind`, and related enums in [`crates/volicord-types/src/values.rs`](../../../crates/volicord-types/src/values.rs). | Adapters, Core, Store, and tests share one Rust representation for controlled values. | Exact value meaning still belongs to API value-set and method Reference owners; enum presence alone is not a product contract. | `typed_requests_derive_documented_operation_categories` and closed-shape request tests in [`crates/volicord-types/src/lib.rs`](../../../crates/volicord-types/src/lib.rs). |
| Canonical request hashing | Idempotency replay needs request identity that is stable across JSON property ordering and formatting. | `canonical_json_bytes`, `canonical_json_sha256`, and `canonical_request_hash` in [`crates/volicord-types/src/canonical.rs`](../../../crates/volicord-types/src/canonical.rs); preflight hashing in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs). | Replayed committed calls can compare a deterministic request hash instead of raw input text. | The hash depends on the typed request representation; schema changes must be considered with idempotency and Reference owners. | `canonical_json_hash_is_order_stable`, `typed_request_hash_ignores_raw_order_and_preserves_semantic_differences`, and `typed_request_hashes_are_stable_across_public_request_serialization` in [`crates/volicord-types/src/lib.rs`](../../../crates/volicord-types/src/lib.rs); `idempotency_replay_returns_stored_response` in [`crates/volicord-core/src/pipeline.rs`](../../../crates/volicord-core/src/pipeline.rs). |
| Test fixture composition through `volicord-test-support` | Cross-layer tests need disposable Runtime Home setup, registered projects and Agent Connections, and request builders without putting fixture code in production crates. | `TempRuntimeHome`, `CoreFixture`, request builders, and Store inspection helpers in [`crates/volicord-test-support/src/lib.rs`](../../../crates/volicord-test-support/src/lib.rs). | Tests can compose Store, Core, MCP, and conformance paths consistently while keeping runtime data under temporary directories. | Fixture helpers can make setup easy to reuse; assertions still need to route back to Reference owners for product meaning. | `tests/conformance/baseline.rs`, `tests/integration/mcp_connection.rs`, and helper tests such as `disposable_runtime_home_stays_under_system_temp` in [`crates/volicord-test-support/src/lib.rs`](../../../crates/volicord-test-support/src/lib.rs). |

## How to use this page

When making a narrow change, use this page to identify the implementation
structure you are touching. Then use the [Implementation Guide](change-guide.md)
to find the exact Reference owner and test layer. Do not add new behavior
because it "fits" a pattern; add behavior only when the applicable owner defines
it or when an owner gap has been resolved.
