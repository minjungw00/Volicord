# Final-output authority disclosure

## Context

Core can return a fresh `AuthorityReceipt` with `volicord.status`, but a current
receipt is useful at the end of an agent turn only if the host exposes it
without asking model-authored prose to preserve or interpret it. In the
existing source structure, the user-visible receipt path is coupled to the
Detective profile Stop hook. That hook can place a validated receipt on a
separate host UI surface, but its allow-or-deny decision is a different
responsibility from final-output disclosure and is not available to the Record
profile.

The MCP mutation refresh and the CLI Stop phase also validate adjacent copies
of the same status/receipt relationships. Separate validators can drift by
accepting different subsets of the owner-defined identity, state, Task, scope,
Change Unit, evidence, and close facts.

This decision explains implementation structure. The focused Reference owners
continue to define the exact receipt, refresh, host-support, fallback, and
output behavior.

## Decision

Use one adapter-independent final-output authority-disclosure path, separate
from Detective Stop enforcement.

1. A supported final-output event requests a fresh, read-only
   `volicord.status` result for the selected project and Task at event time. A
   replayed historical operation result, a preceding mutation response, and a
   preceding Stop result are not freshness sources.
2. A Core-owned typed validator consumes the status result and candidate
   `AuthorityReceipt` together. It checks every correspondence required by the
   focused owners rather than a consumer-selected subset. MCP mutation refresh,
   Detective Stop, and final-output disclosure use this same validator. The
   validator returns typed validation facts, not host-specific text.
3. The CLI converts the validated result into one in-memory disclosure plan. A
   selected Task yields either the complete canonical receipt or a bounded,
   Task-specific `volicord status` fallback. A missing Task, failed refresh, or
   malformed or mismatched result becomes an explicit owner-defined fallback or
   diagnostic outcome; it never fabricates a receipt or emits a partial one.
4. Supported Codex and Claude Code adapters translate that plan to their
   host-native fixed UI surfaces. Profile-independent capability and managed
   configuration planning make the disclosure path available to both Record
   and Detective profiles. Generic, user-managed, unsupported, inactive, or
   degraded paths expose only the fallback and diagnostic behavior their
   Reference owners support; they do not claim a host surface was installed or
   observed.
5. Detective Stop remains a separate consumer. It may use the same fresh
   validation facts while deciding its host-native allow-or-deny result, but
   that enforcement result is not the canonical final-output display. Record
   profile disclosure remains non-blocking.

The disclosure plan is an adapter projection, not a new Core result, public
schema, Store record, or authority source. It is rebuilt for every final-output
event, is never persisted or cached as current authority, and is never supplied
by model prose or generated instructions. No new public API method, table, or
storage migration is introduced by this decision.

## Consequences

- Final-output authority disclosure no longer depends on activating the
  Detective profile or reaching its Stop allow path.
- MCP refresh, Stop enforcement, and final-output display cannot independently
  weaken receipt/status correspondence checks.
- A disclosure failure cannot silently reuse older authority and does not
  change Core state merely to produce UI output.
- Host byte limits are handled by a complete-receipt-or-fallback choice, not by
  truncating canonical JSON or dropping receipt fields.
- Host configuration fixtures and renderer tests establish generated adapter
  bytes. They do not prove that an actual Codex or Claude Code version loaded,
  displayed, or preserved the intended UI surface; that evidence requires a
  live-host run.
- Exact public behavior, supported environments, command text, byte budgets,
  and non-guarantees remain in the focused Reference owners.

## Compatibility and migration

This is part of the intentional pre-major `0.8.0` clean-break batch. Existing
managed Record and Detective host projections must be regenerated by rerunning
the exact supported init workflow. The implementation does not retain a second
legacy final-output path, a compatibility alias, or a fallback to a cached Stop
receipt. Existing unmanaged or conflicting host configuration is not
overwritten; the administrative workflow reports the owner-defined conflict or
recovery action.

The change adds adapter behavior and managed host configuration, not a public
API or storage shape. It therefore needs no Runtime Home conversion or schema
baseline change. Version impact is assessed once for the surrounding `0.8.0`
public-contract batch rather than by assigning a separate version increment to
this cluster.

## Rejected alternatives

- Asking instructions or model-authored final prose to repeat the receipt was
  rejected because generated text is neither a fixed host UI surface nor an
  authority source.
- Reusing the latest mutation, replay, or Stop receipt was rejected because a
  historical receipt is not current status.
- Keeping separate MCP, Stop, and final-output validators was rejected because
  their accepted field sets and failure behavior can drift.
- Requiring the Detective profile was rejected because disclosure and
  enforcement have different responsibilities.
- Persisting a final-output receipt or adding a new public method or table was
  rejected because the display is derived from a read-only current status.
- Truncating the receipt was rejected because partial canonical authority JSON
  changes meaning; the bounded fallback preserves an exact retrieval path.
- Treating generated fixture output as proof of live host UI behavior was
  rejected because host loading and presentation remain external observations.
